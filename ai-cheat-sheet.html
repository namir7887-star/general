00Fundamentals

the shapes every topic uses: one call, a tool, the loop, forced tools, files the code reads, MCP

intvw

Read this line first. Every later stop is one of these shapes with a different problem around it.

F1One call to Claude

every topic has this claude() helper

Each demo calls the Messages API with plain fetch. The body must have model, max_tokens and messages; everything else is optional.

  • The key comes from intvw/.env: npm start runs node --env-file-if-exists=../../.env src/main.mjs.
  • The API remembers nothing. Every call resends the whole messages array, so the model knows only what you send.
  • text(r) takes the first text block of a reply, or says why there is none.

F2What you send, what you get

the request and the reply, field by field

A request is a model, a token limit, the messages, and optionally a system prompt, tools and a tool choice. A reply is a list of content blocks plus why it stopped and what it cost.

F3A tool = Name + Description + Input schema

N, D, I

A tool is three fields. The model reads all three on every call, picks a tool by its description, and fills the arguments to match the schema. Your code runs it.

  • Name (N): what the model asks for, and what your code switches on.
  • Description (D): how the model decides when to use it. Write it like an instruction.
  • Input schema (I): JSON Schema of the arguments. required lists the must-have keys, one list per object level.
  • enum limits a value to fixed choices, e.g. { type: 'string', enum: ['EASY', 'HARD'] } (21).
  • MCP calls the same three name, description, inputSchema; Claude wants input_schema (renamed in 12).
  • Descriptions are prompt tokens on every call: 40 tools cost about 6,000 tokens before the question (14).

F4The agent loop

the model asks, your code runs, repeat until it stops asking

One call cannot run your code. Loop: call, and while stop_reason is tool_use, run every tool it asked for and send each result back with the same id.

  • Push the assistant content first, then ONE user message holding every tool_result.
  • Every tool_use needs a tool_result with its tool_use_id, or the next call fails. A refused or failed tool still gets one, with is_error: true (02).
  • Put a cap on the loop: for (let step = 1; step <= MAX_STEPS; step++) (34).

F5Force a tool to get an object back

tool_choice = structured output

When code needs fields, not prose, force the call. The reply is then a tool_use block and its input is a ready object: no text to cut up.

  • tool_choice: { type: 'tool', name: 'plan' } = it must call that one tool (05, 13, 21, 27, 35, 61).
  • tool_choice: { type: 'any' } = it must call at least one of the tools; it may call several (08 router).
  • No tool_choice = auto: it may answer in plain text instead (52).

F6Agents never talk to each other

your code carries the text

"Agent B" is one more call with its own system prompt. "Send it to B" means your code pastes the text into B's messages, labelled with where it came from.

F7Files the code reads

agents, commands, skills, AGENTS.md

The model never opens these files. Your code reads them, splits the front matter from the body with split('---'), and pastes text into a call.

F8MCP in one page

JSON-RPC between your agent and a tool program

An MCP server is a separate program that serves tools. Your agent (the client) talks to it with JSON-RPC 2.0. Claude never talks to the server: it sees the tool list your code passes on, and your code runs each call.

  • A request has jsonrpc: '2.0', an id, a method, params. The reply carries the same id and either result or error: { code, message }.
  • A notification has no id and never gets a reply.
  • Two renames where the protocols meet: MCP inputSchema becomes Claude input_schema; Claude input becomes MCP arguments.
  • stdio transport: stdout carries only protocol lines, so logs go to stderr. Shut down by closing the server's stdin.
  • Error codes: -32700 not JSON, -32601 unknown method, -32602 unknown tool or bad argument, -32002 this server's own "not initialized".
  • The demo speaks spec 2024-11-05. Spec 2026-07-28 drops initialize: every request carries its version in _meta.

F9What vs what

tool, skill, command, agent file, hook, guardrail, MCP

From intvw/WHAT-VS-WHAT.md. The names blur in interviews; the trigger is what tells them apart.

  • Side effects = tool. Knowledge = skill. Called by name = command. A role = agent file. Must never be skipped = hook or guardrail (code, not prompt).
  • Facts = RAG. Style = fine-tuning. Facts that must outlive a chat = memory. Prompt caching saves money but is not memory.
  • The model reads, explains and suggests. Code computes, decides and checks (13).

CCourse: the home assignment

5,000 labelled tickets: classify each one and draft a reply, solved step by step

intvw/course

The assignment: build a system that classifies every new ticket and drafts a reply; deliver working code and a README that explains the decisions (4 to 6 hours). Shared code lives in course/data/lib.mjs; data in course/data/.

split, embeddings, nearest, prices

intvw/course

You see nearest 972/1000 right, $0, 1.2 s; Haiku 975/1000, 21 s, and 3 of 100 labels changed on re-ask. At a million tickets a day Haiku costs about $5,760 a year.

C3Measure the classifier

one accuracy number hides the costly category

intvw/course/03-measure-classifier

97.2% overall, but a confusion matrix shows complaint recall is 40%: the category that matters most is wrong more often than right.

  • Recall = matrix[c][c] / the row sum (of the real X, how many found). Precision = matrix[c][c] / the column sum (of those called X, how many really are).

You see accuracy 972 of 1000; complaint recall 40%, precision 95%.

Run no key.
